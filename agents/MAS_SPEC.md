# AAA-RNS — MAS 설계서 (일반화판)
## Multi-Agent System + Multi-Agent Transactive Memory (MATM)

| 항목 | 내용 |
|---|---|
| 대상 | **모든 회사·모든 연구과제** (온보딩 시 자동 구성) |
| 문서 버전 | v2.0 (일반화판) |
| 원천 | 특정 정부과제 특화 AAA-RNS v1.5.x 의 MAS 설계를 과제 중립으로 재작성 |

## 1. 설계 원칙

이 시스템은 연구노트를 "잘 써주는" 시스템이 아니라 **거짓을 쓸 수 없는** 시스템으로
설계했다. 생성 능력보다 차단 능력이 먼저다.

**규칙 1 — 무증거 무기재.** 모든 서술 문장은 증거원장 증거ID `[E#]` 최소 1개에
매핑된다. 인정 소스 3종: 업로드 원본 / 확정 과거 노트 / project.json.
모델의 사전 지식은 증거가 아니다.

**규칙 2 — 과거와 모순 금지.** 새 노트의 모든 주장은 확정된 과거 노트 전체와
대조된다. 값이 실제로 바뀐 경우 변경 근거 증거를 요구한다.

**규칙 3 — 게이트 전원 통과.** G1~G4 중 하나라도 FAIL 이면(strict 모드)
`_REVIEW/` 반려. advisory 모드에서는 지적사항을 「보완 항목」으로 보존한 채 저장.

**규칙 4 — 데이터-프롬프트 이중 기재 금지 (일반화의 핵심).** WP 구조·지표
카탈로그·목표치·일정·인력은 프롬프트에 쓰지 않는다. 에이전트는 반드시
`data/*.json` 을 조회한다. 과제가 바뀌면 데이터만 바뀌고 에이전트는 그대로다.

기억은 단일 저장소 대신 **분산 전문화(Transactive Memory)** — 각 에이전트가
전문 영역만 기억하고, "누가 무엇을 아는지" 디렉토리(A16)를 공유한다.

## 2-1. 그룹 구조와 통신 규약

### 그룹 리드와 완결성 책임
각 계층의 ★리드는 그룹 산출물의 완결성을 확인한 뒤에만 다음 계층으로 패킷을
발신한다. 리드가 확인하는 것: 필수 필드 충족 · 담당 에이전트 전원의 슬롯 기록 ·
미해결 상충의 명시(숨김 금지).

### 블랙보드 (그룹 내부 통신)
그룹 내부는 메시지 교환이 아니라 **공유 블랙보드**를 쓴다 — 이 시스템에서
블랙보드는 곧 `data/*.json` 파일이며, **단일 작성자 원칙**이 강제된다:

| 블랙보드 | 유일 편집자 | 다른 에이전트 |
|---|---|---|
| data/project.json | A1 | 읽기 전용 |
| data/planner.json | A2 | 읽기 전용 |
| data/metrics.json (catalog) | A4 | 읽기 전용 |
| data/metrics.json (actuals) | A13 | 읽기 전용 |
| data/config.json (note.*) | A5 (사람 승인 후) | 읽기 전용 |
| ledger/evidence_ledger.json | A8 | 제안만 (A21·A22 는 A6 경유) |
| notes/*.json (초안) | A12 | 배치안·다듬기안 제출 (A23·A24·A25) |
| data/audit.json | A25 | append-only, 수정·삭제 불가 |

### 계층 간 typed packet (스키마 고정)
계층 사이는 자유 대화가 아니라 **형식이 고정된 패킷**으로만 통신한다.
패킷은 전 단계 완결성 검사를 통과해야 처리되며, 같은 패킷의 재수신은 무시된다(멱등).

```
① ProjectFrame   (L1→L2·L3) { project_code, period, wp[], kpi_catalog[],
                               regulation_profile, source_flags[] }
② EvidenceBundle (L2→L3)    { note_period, entries[{id,kind,content,date,source,sha256}],
                               conflicts[{a,b,kind,reason}] }
③ DraftNote      (L3→L4)    { note_id, sections, citations_map,
                               preflight:{g1_pass,checked_by:"A17"} }
④ GateVerdict    (L4→A0·L3) { note_id, gates[4], decision, violations[] }
⑤ EscalationTicket (임의→A0) { from, reason, evidence_refs[], attempts }
```

### 재작업 루프와 에스컬레이션
GateVerdict 가 FAIL 이면 A0 가 위반 유형별로 담당을 지정해 재작업시킨다:
무인용·유령인용→A17→A12 · 수치·단위→A10/A13 · 기간·중복→A15 · 문체·금지표현→A16 ·
규정 미충족→A5 확인 후 A12. **같은 노트의 재작업 3회 초과 시 사람에게 에스컬레이션**
하고, 전 과정은 A17 감사로그에 남는다.

## 3. 파이프라인

```
업로드/직접 기록
 → A7 시점 판별 (사용자 확정 필수)
 → A4 파싱·해시 → A8 증거원장 등재
 → A7·A8·A9 집필 (전 문장 [E#])
 → 결정론 게이트 G1~G4 (코어가 브라우저에서 직접 실행 — LLM 비의존)
 → PASS: 서명 대기 → 기여자 서명 → 최종 승인(교차 승인) → 확정(sealed)
 → FAIL: advisory 저장 + 보완 항목 / strict 반려
 → A14 문서 3종 → A15 지표 반영 → A16 기억 갱신 → A17 감사 기록
```

**확정 해시 체인**: `seal_hash = SHA-256(content_sha256 + prev_seal_hash)` —
확정 노트 전체가 사슬로 연결되어 어떤 노트의 사후 변조도 체인 검증에서 탐지된다.

## 4. 구현 형태

- **결정론 코어** (`js/core/`) — 파서·분석기·생성기·원장·게이트·해시가 순수 JS 로
  구현되어 브라우저에서 직접 실행된다. 기록 차단 권한은 항상 이 코어가 가진다.
- **LLM 프롬프트 템플릿** (`agents/prompts/A*.md`) — 집필 보조·의미론 검증 강화용.
  `{{변수}}` 는 온보딩 시 주입되며, 어떤 엔진(Claude·Gemini·사내 LLM)과도 연결 가능.
  LLM 이 없어도 시스템은 완전히 동작한다 (직접 작성 + 결정론 게이트).
